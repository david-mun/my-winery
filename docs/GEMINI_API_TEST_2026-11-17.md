# Gemini 실제 이미지 분석 테스트 — 2026-11-17

상태: API 호출·추출 검증 완료, 앱 연동/자동 저장 인수는 미완료.

사용자가 제공한 영수증 1장과 와인 6병 사진 1장으로 실제 키를 사용해 테스트했다. 영수증은 대표자명·연락처·주소·사업자번호 및 하단 전표 식별 영역을 가리고 EXIF를 제거한 이미지로 보냈다. 와인 사진은 전체 사진 및 말보로 썬 한 병의 crop으로 비교했다. 원본 이미지와 `.env.local`은 변경하지 않았고 키는 출력하지 않았다. 정답 CSV/예상 가격/와인 목록을 프롬프트에 제공하지 않았다.

실제 모델 요청은 총 10회(성공 응답 4, 400 2, 404 1, 503 3)다. 성공 응답은 요청별 단일 표본이며 모델 우열이나 안정적인 처리 시간을 입증하지 않는다. 여러 병 분석은 진단용으로 허용한 것이고, 현재 설계의 `wine_label` 단일 병 의미 계약을 통과했다는 뜻은 아니다.

## 영수증 검수

| 항목 | 반환 금액 |
|---|---:|
| 무초마스 스파클링 | 16,900원 |
| 엘에네미고 샤르도네 | 36,900원 |
| 마스카 델 타코 수수마니엘로(이름 오독 검수 필요) | 24,900원 |
| 조지 미쉘 + 러시안 잭 세트 | 39,900원 |
| 블라송 루즈 브뤼 | 24,900원 |
| 합계 / 실결제액 | **143,500원** |

- 두 성공 응답 모두 상품 줄 5개, 세트 구성 포함 6병으로 해석했다. 영수증의 POS 총수량 5와 실제 병 수를 구분했다. 세트는 한 줄만 합산하고 두 연결의 `allocated_amount`는 NULL이었다.
- 할인 0원으로 반환되어 `sum(lines) - discount = paid_amount`가 일치했다. 구매일은 전표 영역을 가린 입력에서 확인 불가하므로 NULL이었다. 기존 데이터의 구매일로 자동 보충하지 않았다.
- 3.1 응답은 원문의 두 자리 `22`를 2022로 확장해, 4자리 명시만 허용한 테스트 지시를 따르지 않았다. 확인 전 채택하면 안 된다.
- 3.1 응답은 마스카 델 타코에 해당하는 줄의 `name_original`을 사진에 없는 `I Muri Susumaniello`로 채웠다. 연결 생산자 제안도 검증되지 않았다. JSON 형식 통과가 상품 동일성을 보장하지 않는 실제 사례다.
- `status=ok`여도 날짜 NULL, 잘못된 경고 Pointer `/purchased_on`, 후보 기준 `/observed/...` 대신 `/name_ko` 등의 잘못된 근거 Pointer가 있었다. 서버 재검증과 사용자 확인을 생략할 수 없다.

## 구현에 반영할 내용

1. 모델 목록 조회 성공과 실제 이미지 생성 호출 가능 여부를 따로 검증한다. 모델 ID는 서버 설정으로 관리하고 실제 요청 404/503을 사용자에게 구분해서 안내한다. 자동 유료 전환은 하지 않는다.
2. 호출용 스키마는 작업별로 필요 분기만 남기고 참조를 펼친다. 이번에는 배열 개수/숫자 범위/문자열 길이 등 복잡도 유발 제약을 호출용에서 제외하자 응답을 받았다. 원본 JSON Schema 검증은 그대로 유지했다. 단순히 제약을 빼면 후보 ID·빈티지·척도 위반이 생기므로 값의 의미/범위는 서버에서 검사해야 한다.
3. 숫자 척도를 작은 enum으로 표현하는 등 호출용 제약을 개선하고, 정확한 Pointer 예제를 프롬프트에 넣어 재검증할 필요가 있다. 원어명 보충은 번역과 상품 추론을 분리하고 모르는 상품명·생산자를 확정하지 않는다.
4. 원문/구매 사실 추출과 상품 상세·스타일 제안을 한 번에 많이 요구하면 검수 지점이 늘어난다. 원문 우선의 구매 초안을 만들고, 품목별 라벨/사용자 선택으로 상품 상세를 보완하는 현재 설계 방향을 유지한다. 단계 분리의 품질 개선은 아직 별도 비교 실험하지 않았다.
5. 근거 유효성·소유권·회계·중복·필수값 검증과 사진 대조 후 저장한다. 이 테스트의 JSON을 그대로 DB 입력으로 사용할 수 없다.
