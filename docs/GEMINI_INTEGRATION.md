# Gemini 사진 입력 구현 — 2026-11-17

이 문서는 현재 실행되는 구현의 기준이다. 11월 15일의 [v1 설계](GEMINI_PHOTO_ANALYSIS.md)와 [첫 실제 이미지 테스트](GEMINI_API_TEST_2026-11-17.md)는 검토 이력으로 보존한다. 사용자 요청에 따라 기기 OCR·텍스트 붙여넣기 파서는 제거하고 Gemini 사진 분석과 직접 입력을 제공한다.

## 설정과 API

- 서버 `.env.local` 또는 배포 secret: `GEMINI_API_KEY`.
- `GEMINI_MODEL`: 기본 `gemini-3.1-flash-lite`. 2.5 Flash-Lite는 이 계정에서 실제 요청 404였고, 3.5의 일시적 503도 확인했으므로 현재 실제 성공한 안정 모델을 기본값으로 선택했다. 모델 접근·요금·한도는 계정에서 따로 확인한다.
- `GEMINI_ANALYSIS_ENABLED=false`: 외부 분석 중지. 미설정이면 키가 있을 때 활성화. 공개 데모에서는 분석 입력을 제공하지 않는다.
- 사용량 제한은 기존 `consume_rate_limit`을 이용한다. 사용자 분당 3회/프로젝트 분당 10회, 사용자 24시간 20회/프로젝트 24시간 100회(고정 윈도). DB 원자 카운터이며 프로세스 메모리 카운터가 아니다. 거부 요청도 일부 카운터를 소비할 수 있고 공급자 503 재시도는 같은 요청 안에서 최대 1회다. 별도의 전역 동시 실행 lease는 이번 구현에 추가하지 않았다.

`POST /api/analysis/receipt`, `POST /api/analysis/wine-label`에 multipart `file` 1개와 `consent=true`를 보낸다. 선택 전 파일은 10MiB/40MP, 서버로 보내는 이미지는 최대 3MiB다. JPEG/PNG/WebP signature와 디코딩을 검사하고 최대 긴 변 2,000px/WebP로 다시 인코딩하여 EXIF를 제거한다. 임의 외부 이미지 URL/타인 Storage 경로는 입력으로 받지 않는다. 여러 라벨을 합친 분석은 등록 대상으로 받지 않고 한 병의 라벨 영역으로 자르도록 안내한다.

응답은 `task`, `model`, `schema_version`, `analysis`, `warnings`다. 영수증은 `schema_version: "3.0"`, 라벨은 `"2.0"`이다. 실패는 기존 앱과 동일한 `{error: "한국어 안내"}`이며 400/401/403/413/415/422/429/502/503/504를 구별한다. 모든 응답은 `private, no-store`. 공급자 오류 원문·이미지·키·개인 원문을 로그에 출력하지 않는다. 모델은 자동으로 다른 유료 모델로 변경하지 않는다.

현재 소스는 [공유 계약](../lib/analysis/contracts.ts)이다. 기계 검토용으로 [영수증 v3 스키마](schemas/gemini-receipt-v3.schema.json), [와인 라벨 v2 스키마](schemas/gemini-wine-label-v2.schema.json)를 함께 보관한다. 기존 영수증 v2의 `details` 없는 초안은 null로 호환 처리한다. v1 JSON은 현재 API에 입력하지 않는다.

## 영수증 v3 상품 상세 후보 — 2026-11-18

사용자 요청으로 각 `lines[].wines[]`에 nullable `details`를 추가했다. `raw_label`과 `wines.name`은 인쇄 원문을 보존하고, `details`에서만 상품 지식으로 정식명·영문명·원산지 등을 추정한다. 제품을 좁히지 못하면 전체 null, 일부 상세를 모르면 해당 필드 null/빈 배열이다. 웹 검색이나 공식 자료 검증을 수행하지 않으므로 모든 상세는 미검증 후보이며 모델의 `confidence`도 사실성 보증이 아니다.

| 필드 | 의미 |
|---|---|
| `name_ko`, `name_en` | 한글 정식명·영문명 후보 |
| `producer`, `country`, `region`, `grapes` | 생산자·국가·지역·품종 후보 |
| `alcohol_percent` | `{min,max}` 도수 범위. 단일 값은 min=max, 미확인은 null |
| `confidence`, `notes` | 모델의 high/medium/low 판단과 모호한 상세 설명 |
| `summary_ko` | 와인 자체에 대한 짧은 한국어 설명. 개인 시음 노트가 아님 |

사진에 없는 빈티지 연도는 후보 이름에서도 제거한다. 역전된 도수 범위는 null로 정리한다. 후보에는 DB ID·가격·빈티지 필드가 없으며 기존 회계·세트·할인 규칙을 바꾸지 않는다. 구매 폼은 후보 상세를 보여 주고 `후보 와인명 사용`을 눌렀을 때 이름·생산자와 신규 마스터용 `summary_ko → description`, `name_en → name_original`을 채운다. 원문 수정·수동 이름 편집·다른 컬렉션/카탈로그 선택 시 이전 후보 값을 지운다. 상세 전체를 저장 RPC에 보내거나 기존 와인 마스터에 자동 덮어쓰지 않는다.

2026-11-21부터 `vintage_label`은 영수증/라벨의 선택 입력이다. 요청용 스키마는 Zod 입력 스키마에서 생성하여 required에서 제외한다. 생략·null·빈 값은 서버에서 UNKNOWN으로 정규화하며 유효한 기존 NV/연도는 유지한다. UI에는 빈티지 입력·전용 표시를 제공하지 않는다. 라벨 응답에도 nullable `summary_ko`를 추가하고 검수 후 와인 설명으로 저장한다. 요약은 라벨에서 확인한 정보의 한국어 요약이며 개인 경험·평점·빈티지 설명을 생성하지 않는다.

## v1에서 단순화한 이유

실제 테스트에서 전체 v1 스키마는 Google의 상태 수 제한에 걸렸고, 후보 ID·JSON Pointer·AI 제안 값도 종종 틀렸다. v2는 다음과 같이 줄였다.

- 영수증 와인은 줄 내부에 이름·빈티지·수량을 중첩한다. 모델이 DB ID·후보 참조·배분 가격을 반환할 수 없다. 최종 소유자 와인 연결과 세트 배분 NULL은 기존 저장 RPC가 담당한다.
- 와인 상세는 `name`, `producer`, `wine_type`, `country`, `region`, `grapes`, `vintage_label`, `alcohol_percent`, `bottle_volume_ml`, `label_description`이다. `evidence`는 허용된 필드명과 인쇄 문구이며 임의 Pointer를 사용하지 않는다.
- 향·타닌·음식/스타일 제안·외부 점수/URL·개인 평점/시음 기록은 반환 대상이 아니다. 라벨 v2는 인쇄된 상세만 추출하며, 영수증 v3의 상품 지식 보충은 별도 `details`에서만 허용한다.
- 문자열 길이·숫자 범위·목록 상한은 호출용 스키마에서 단순화하되, 반환 시 엄격한 Zod 검증을 유지한다. 근거가 없는 와인 상세는 비워 두고 사용자에게 알린다. 2자리 영수증 연도를 4자리 빈티지로 확장하지 않는다. 사진 근거의 진실성은 구조 검사로 보장할 수 없으므로 항상 원본 대조가 필요하다.

## 화면과 저장

사진을 고르는 것만으로 외부 전송하지 않는다. 로컬 canvas에서 드래그로 가리기/자르기, 상단/하단 가리기, 키보드 비율 좌표로 영역 지정을 제공한다. 사진 편집 중에는 분석/저장을 차단하고, 편집 또는 교체하면 이전 동의·결과를 초기화한다. 전송할 이미지 확인 체크 후 `Gemini로 분석`을 누른다. 무료 처리의 제품 개선/검토 가능성과 개인정보 제출 금지 안내를 전송 전에 표시한다.

응답을 받은 뒤 `초안에 적용`을 별도로 누른다. 기존 입력을 교체하는 경우 확인하며, 분석 중 입력한 내용을 늦은 응답이 자동 덮어쓰지 않는다. 취소/사진 교체/화면 종료 시 요청을 취소하고 이전 응답을 무시한다. 실패 시 현재 입력·사진을 유지하며 직접 입력할 수 있다. 초기 페이지 hydration이 끝날 때까지 파일 선택을 비활성화해 초기 선택 유실을 막는다.

- **영수증:** 구매일·매장명·일반/세트 줄·금액·전체 할인·병 수를 기존 구매 폼에 넣는다. 미확인 금액은 빈 입력이며 합계를 확정 표시하지 않는다. 39,900원 세트 한 줄, 병별 가격 미배분, 전체 할인 1회 차감을 유지한다. 사용자 원본 대조 체크와 기존 `receiptInput`/RPC 무결성 검사를 통과해야 저장한다. 매장/품목의 개인 컬렉션 연결은 자기 데이터에서만 수행한다. 현재 영수증 분석은 상품명 기반 구매 초안이며 와인 생산지·도수 등 상세를 구매 RPC에 새로 넣는 확장은 하지 않았다.
- **와인:** 실제 인쇄 언어를 유지한 이름과 확인된 상세를 기존 등록 폼에 넣는다. 명시되지 않은 종류는 확인 필요로 남긴다. 생산자와 이름이 별도로 읽히면 사진에서 읽은 두 문자열만 합쳐 같은 품종의 다른 상품과 혼동을 줄인다. 빈티지·도수·용량은 선택 메모에 라벨을 붙여 저장하고 구매나 현재 재고를 만들지 않는다. 기존 이름/원어명 후보가 있으면 기존 상세 링크를 제공하고 중복 신규 저장을 막는다. 이름/생산자 변경 등 모호한 동일성은 사용자 확인 대상이다.
- **사진:** 사용자 선택 시 기존 private Storage 업로드. 와인 저장 후 사진 업로드가 실패하면 생성 ID를 유지하고 사진만 재시도하므로 와인을 다시 만들지 않는다. 구매 사진도 기존 저장 후 첨부 흐름을 유지한다.

새 테이블은 추가하지 않는다. 설명·영문명 저장에는 `202611210001_receipt_wine_description.sql`의 RPC 변경이 필요하며 승인된 원격 적용 후 배포한다. 기존 마스터·사용자 데이터·원본 스냅샷·키는 자동 변경하지 않는다. 배포 시 Vercel 서버 키/선택 모델 설정을 사용한다.
